### AWS KMS – Key Concepts & Core Principles

#### General Characteristics
- KMS is a **regional and public** AWS service.
- Keys **never leave the region** in which they are created.
- Compliant with **FIPS 140-2 Level 2**.
- Manages both **symmetric** and **asymmetric** cryptographic keys.
- Supports operations such as **encryption**, **decryption**, **signing**, and **verification**.

---

### Core Concepts
- **KMS Key (Customer Master Key / CMK)**: A logical container for key material.
    - Contains **metadata** (ID, ARN, key policy, tags).
    - Backed by **physical key material**.
    - Key material can be **generated by AWS** or **imported** by the user.
    - Supports **key sizes up to 4 KB**.

---

### GenerateDataKey API
- Used for encrypting **data larger than 4 KB** (envelope encryption).
- Returns two versions:
    - **Plaintext key**
    - **Encrypted key** (wrapped with the KMS key)
- Typical process:
    1. Use the plaintext key to encrypt the data.
    2. Discard the plaintext key after encryption.
    3. Store the **encrypted data** along with the **encrypted data key**.

---

### Key Types and Ownership Models
- **Customer Managed Keys**
    - Created and managed by the customer.
    - Full control over rotation, policies, tags, and aliases.
    - Supports automatic key rotation (optional).
- **AWS Managed Keys**
    - Created automatically when using AWS services with encryption enabled.
    - Limited control and visibility.
    - Automatically rotated by AWS.
- **AWS Owned Keys**
    - Fully controlled and used internally by AWS.
    - No visibility or direct access for customers.
    - Operate entirely in the background.

---
### Regional Behavior
- KMS keys are **isolated per region**.
- Keys do not leave their region under any circumstance.
- **Multi-region keys** can be explicitly created if cross-region encryption support is needed.    

---
### Key Policies 
- **Each KMS key has exactly one Key Policy**.
- A **Key Policy is a resource-based policy** that defines who can use and manage the key.
- By default, **KMS keys do not automatically trust the AWS account root user** or any IAM identities.
- **Access control is based on combining**:
    - **Key Policies** (required)
    - **IAM Policies** (optional, but only effective if allowed by the Key Policy)
    - **Grants** (optional, used for temporary or delegated access)
- **To enable IAM policies**, the Key Policy must explicitly **trust the AWS account** (using `"Principal": {"AWS": "arn:aws:iam::ACCOUNT_ID:root"}`).
- Best practice:
    1. Trust the **account** via the key policy.
    2. Grant **fine-grained access** to IAM users/roles via IAM policies or grants.
